<Chapter id="figma" title="The system in Figma">

Foundations on Figma variables: colours in a light (gold) and a dark theme, type, spacing, corner radius and shadows. Every component has its own spec: anatomy, types, sizes, states and the rules for using it, so a developer never has to guess.

<Note>The spec pages from the Figma file are being added.</Note>

</Chapter>

<Chapter id="code" title="From Figma to code" sub="One token, followed from the Figma variable to the product.">

Tokens are generated from the Figma variables, and the components use nothing else: no raw colours, sizes or font names. PrimeReact gives the behaviour, the keyboard support and the ARIA; it runs without its theme, so every pixel comes from the system. Change a variable in Figma and the product follows, in both themes.

<TokenAnatomy />

Every component page in the Storybook has the same parts: its status, a playground, when to use it and what to use instead, examples that run as tests, the design decisions, accessibility (WCAG 2.2 AA in both themes) and a map from the Figma properties to the props, so a developer reads the Figma file and the code the same way.

<Chapter id="audit" title="The UX audit" sub="The whole app walked as one system, with three questions.">

Is it clear where everything is and what it is called? Does the same thing look and read the same everywhere? Which parts is the system itself missing? I went through the seven pages of the menu, Profile, the avatar menu and the bell on a 1440 desktop.

<Finding id="C-1" severity="High" title="Six date formats" fix={<>One format with the month as a word, so it can’t be read two ways: <i>10 Nov 2026, 12:49</i> in tables, periods as <i>1–7 Nov 2026</i>, “3 h ago” only in the bell.</>}>
  <p>The most visible one. In a US office 10/11/26 reads as 11 October, and in a payments product the date is evidence.</p>
  <Formats before={["10/11/26, 09:52:07", "2026/11/10 12:49:41", "24/09/25, 14:49:41", "24/09/2025, 14:49:41", "2026-11-01 – 2026-11-07", "2026-11-08, 16:14:05"]} after="10 Nov 2026, 12:49" cap="one rule in Foundations → Formats, used by every page" />
</Finding>

<Finding id="C-2" severity="High" title="One payment, different IDs and times" fix="One source of data for the Dashboard, Transactions, Invoices and the notifications.">
  <p>The same 0.065769 ETH payment had one ID and time on the Dashboard, another on Transactions, and a third ID in the bell. Someone who opens a row on the Dashboard lands on a different record, which breaks trust in a live demo.</p>
</Finding>

<Finding id="IA-3" severity="Medium" title="Ownership managed in three places" fix="Transfer ownership in the owner’s row in Members; Settings only shows the owner, with a way to Members.">
  <p>The Owner role showed in Members and Profile, but could only be changed in Settings, while every other role changes in Members. Someone handing the company to a colleague goes to Members and finds nothing.</p>
</Finding>

<Finding id="S-1" severity="Medium" title="No Page Header in the system" fix="A Page Header component: title, actions and tabs, one height with or without buttons.">
  <p>Every page assembled its title, buttons and tabs itself. With a button the title sat 4px lower, so the page jumped between screens, and each page named its main action its own way.</p>
</Finding>

I brought nine decisions to the table, each with a recommendation; all nine were accepted.

</Chapter>
